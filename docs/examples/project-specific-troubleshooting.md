# 项目专属故障条目怎么记 —— 4 条嵌入式项目精华范例

> **这个文件是什么**：主手册（`docs/TROUBLESHOOTING.md`）只收与技术栈无关的通用经验（A/B/C 组）。
> 你自己项目的框架、硬件、语言、内部服务的坑，应该记在目标项目 `.agents/TROUBLESHOOTING.md`
> 的 **D 组**里。
>
> 下面 4 条来自本套件的来源项目（ESP32-S3 + Python 服务器的教学产品），
> **它们不是给你照抄的解决方案，而是「一条好的项目专属条目长什么样」的示范**：
> 每条都有「现象 → 判断 → 真因 → 修复 → 可迁移的教训」，而且教训部分对别的技术栈也成立。
> 读完可以删掉这个文件——它只存在于 kit 仓库，安装器不会把它装进你的项目。

## D-例 1：SoftAP 密码不足 8 位 → 板子"开机就重启"

**现象**：设备接上真机，串口无限循环 `ESP_ERROR_CHECK failed ... abort() → Rebooting...`，
屏幕来不及亮，按键也救不回来，看起来像硬件变砖。日志里有一行不起眼的
`wifi:password less than 8`。

**判断**：错误码 `0x300b = ESP_ERR_WIFI_PASSWORD`；`abort()` + 重启循环且发生在
配网初始化函数里 → 是软件参数问题，不是硬件。

**真因（两个错叠加）**：

1. AP 密码用 `%04u` 生成了 **4 位**，而 WPA2-PSK 要求 **8–63 位**。
2. 那行用 `ESP_ERROR_CHECK()` 包裹了一个"配置本身可能错"的调用，
   于是"参数不合法"被升级成 abort——配网正是配置可能出错的路径，在这里 abort = 变砖。

**修复**：密码生成 `%08u`；初始化路径逐级判错返回，不用 `ESP_ERROR_CHECK`，
让设备保持可重试状态。

**可迁移的教训（任何技术栈都成立）**：

- **"错误处理"不要把可恢复的业务错误升级成进程崩溃**；边界入口（配置、用户输入、外部设备）
  尤其如此。
- **只在真实运行环境才走到的路径，"编译通过 + 单测绿"不算完成**（对应通用手册 A3）。
  这条 bug 在主干上躺了三天、PR 正文写着"软件侧全绿"，直到插上真机才暴露。

## D-例 2：构建被超时杀掉，ninja 报 "subcommand failed" 却零错误输出

**现象**：长构建日志最后一行是 `ninja: build stopped: subcommand failed.`，
但提示的 stderr 文件 **0 字节**，日志里搜不到任何 `error:`，看起来像"编译器无声失败"。

**判断**：

- `grep -c 'error:' 日志` = 0、stderr 文件 0 字节 → 几乎肯定是进程被杀，不是代码错。
- 这一段耗时正好等于工具超时时间（约 600 秒）。
- 佐证：`.ninja_log` 在增长、进度计数 `[N/M]` 的 N 在变大 → 构建本身是好的。

**真因**：工具在超时点 SIGTERM 掉构建驱动进程，ninja 的子进程随之被杀，
ninja 只能报"子命令失败"，但被杀的进程没来得及输出任何诊断。

**修复**：**什么都不用修**，重跑同一条命令——ninja 的增量记录已落盘，下一段自动续编。

**可迁移的教训**：

- **"没有错误输出的失败"先怀疑进程生命周期**（被杀、被回收、OOM），再怀疑代码
  （对应通用手册 A4）。
- 判断构建系统健不健康，看它的**增量状态文件**，不要只看日志尾部。

## D-例 3：写了一个摄像头"可调参数"，结果一帧都不出

**现象**：开机自检失败，连续 5 次取帧超时；但能力查询显示该参数"范围 1..63、可写"，
传感器在 I2C 总线上也正常应答。

**真因**：往摄像管线写 `JPEG_COMPRESSION_QUALITY` 这个控制项本身会让编码器停摆
（与调用位置无关：放在流水线哪个阶段都坏）。**"能读到合法范围"不等于"能安全地写"。**

**定位过程（值得复用）**：

1. **对照**：`git checkout <上一个已知好提交> -- 设备源码目录`，重新构建/运行 → 立刻正常。
   排除硬件、排线、构建环境。
2. 用同样源码再构建一次也正常 → 排除"构建环境在产出坏二进制"。
3. **二分**：只把可疑改动加回（`git checkout <引入提交> -- <文件>`）→ 锁定。

**修复**：整块撤掉——收益从未被验证过，却把主功能弄死了，不值得留。

**可迁移的教训**：

- **"能力查询通过 / 接口文档没禁止" ≠ "运行时安全"**；传感器、编解码器、内核参数这类
  贴近硬件/运行时的接口，一次只改一个变量、真机验证。
- 改完必须看**现象**变没变，不能只看日志有没有报错——日志一路"成功"、现象却是坏的。
- `git checkout <好提交> -- <路径>` 做对照 + 二分，是定位"环境/硬件/代码到底谁坏"的快手法。

## D-例 4：设备"插上却连不上"——先查外部配置，别怀疑固件

**现象**：设备插着、串口日志正常、固件没换过，但服务端一台设备都看不到；
日志显示 `WiFi disconnected, retry` 无限重试。

**逐条核对（这次四条里错了两条）**：

1. **服务端地址还是本机当前 IP 吗？** 本机 IP 会随网络变，断网后旧地址直接消失。
   对日志里的 URL 与 `ipconfig`/`ifconfig` 当前地址。
2. **SSID 是当前这个热点吗？**
3. **★ 热点频段对吗？** 该设备只支持 2.4GHz，而手机热点默认常是 5GHz——
   设备根本扫不到，现象与"密码错"一模一样，最容易查错方向。
4. 密码对不对（大小写、全角字符）。

**修复**：重新配网（不用重新编译/烧录），地址填电脑当前 WLAN IP，热点显式切 2.4GHz。

**可迁移的教训**：

- **"明明昨天还能用"的连接问题，排查顺序是：外部配置（地址/网络/凭据/频段）→ 环境 →
  本项目代码**。别一上来就怀疑自己的固件/服务。
- "扫不到"和"密码错"在现象上可能完全相同；错误信息不区分时，要把枚举项和连接失败
  在接口层就分开返回，别让用户猜。

## 小结：D 组条目的写法模板

```
## D<编号> <一句话现象（让人搜得到）>

- 现象：用户/日志实际看到什么（含原始报错原文）
- 判断：用什么 1～3 条命令或观察把它和相似问题区分开
- 真因：机制层面的解释，而不是"重启就好了"
- 修复：可以直接照抄的命令/代码
- 避免/教训：抽出对别的场景也成立的那一句话
```

> 通用手册的维护规则同样适用于 D 组：只追加、编号不复用、订正写新条目并注明"订正 Dx"。
