# 可行性验证与使用边界

## 本轮结论

在“同一台电脑、同一 Git 仓库、各 agent 遵守登记规则”的条件下，工具链可以形成完整闭环。
2026-10-14 在 Windows / Python 3.12 的隔离目录中完成了 77 个实际检查点；
运行的是当前功能分支的工作副本，而非假设默认分支已经包含这些改动。
同时通过 89 项回归（43 项基础/安装 + 17 项会话 + 29 项策略/接管/客户端）和 48 项看板自检。

复现方式：

```text
python scripts/rehearse_workflow.py --report .agents/rehearsal-latest.md
```

脚本真实启动进程、调用 Git、建立工作区、启动 HTTP 服务并读写协作文件。
报告包含每步的命令、预期与实际退出码和输出；预期的冲突拒绝也需要命中正确原因才算通过。
临时仓库和服务在结束时清理，实际项目不作为安装或业务修改目标。

## 实际覆盖的闭环

| 环节 | 验证结果 |
|---|---|
| 安装源复用 | 真实本地 clone 一次，两个项目使用同一个安装器副本 |
| 安装与升级 | 按平台生成文件，升级保留项目定制和已有协作记录 |
| 工作区与占用 | 同工作区重复登记被拒绝；跨 worktree 重叠文件被拒绝；独立文件可登记 |
| 网页指令 | 真实 HTTP 看板聚合会话，POST 指令落盘，回复能由 API 读到 |
| 指令状态 | 收到回执仍保持 open；显式纳入任务后恢复，执行完成才 answered |
| 中断与恢复 | handoff 保留占用，resume 沿用 ID，自己的交接条被回执 |
| 业务验证 | 在已登记范围内修改示例业务文件，运行真实单元测试后提交 |
| 推送 | 向隔离的本地 bare 远端推送 feature 分支，不触及用户远端主干 |
| 收尾 | finish 追加日志、回执关联交接，最终没有悬挂会话、问题或工作区告警 |
| 扩展与清理 | 追加平台、再体检、确认产物被忽略；卸载预览保留记录 |
| 项目策略 | 第二项目仅使用 main，GitHub Flow 正确允许 codex/ 任务分支；回归覆盖 custom 与跨 worktree 继承 |
| 失联接管 | 真实 CLI 执行 inspect / plan / 等待门禁拒绝 / cancel，取消不修改原会话 |

接管成功路径在真实临时 Git 仓库中验证，仅以测试补丁控制时钟：299.99 秒拒绝、300 秒允许；
校验原分支、引用、暂存和未提交文件保持不变。产品没有跳过等待的开关。
额外回归覆盖声明回复、心跳、内容、暂存、提交、分支及策略变化时的拒绝；损坏计划与写入中断保留可追溯状态。

## 客户端和页面验证

使用 `clients --versions` 在本机实际查询了以下 CLI，未启动模型或改变客户端全局配置：

| 客户端 | 本次查询的版本 |
|---|---|
| Codex | 0.162.1 |
| Claude Code | 2.1.263 |
| OpenCode | 1.18.35 |
| Gemini CLI | 0.63.0 |
| Qwen Code | 0.11.1 |

版本可发现与新对话加载是两项检查。以上不证明模型已读取入口；各客户端仍需按 [PLATFORMS.md](PLATFORMS.md) 新建会话验收。
IDE/应用内平台显示“手动验证”，PATH 未找到某个 CLI 不表示该应用未安装。

本地浏览器验证了平台多选、文件清单、Git Flow/GitHub Flow/沿用切换、清空恢复、提示词与命令复制、键盘标签切换。
桌面与 390px 视口无横向溢出，控制台无错误。复制核对以页面“已复制”反馈完成后读取的内容为准。

第一轮演练发现看板的 `--port 0` 输出了无效的 `:0` 地址，修复为系统实际分配的端口后通过。
流程审查同时补齐了 blocked 恢复、交接留言收尾和“已收到/已完成”的区分。
这些是使用流程中的缺口，不能只凭原有单元测试通过就认为没有问题。

## 没有声称验证的部分

- 没有启动 15 个真实 AI 客户端或调用模型；平台入口仍需在对应版本中新开会话验收。
- 没有自动创建 GitHub PR、合并或部署；真实远端操作遵守仓库分支规则与用户授权。
- 没有跨电脑同步、本机以外的身份认证或对源码强制加锁。
- 占用粒度是文件/目录，不支持同一文件不同函数的自动并行。
- finish 的测试文字来自调用者，不是测试真实性的密码学证明；仍需保留真实命令输出与 CI 记录。

开发分支尚未合并时，普通 `git clone` 下载的仍是默认分支。验证开发版本应先确认源码检出的提交，
不要把“功能分支验证通过”表述为“默认安装和线上页面已更新”。

## 下一步最值得改进的方向

| 优先项 | 价值 | 验收方式 |
|---|---|---|
| 常用客户端的真实新会话验收 | 验证发现入口、读取规则及执行检查的实际表现 | 从 Codex / Claude / 当前常用平台开始，记录版本、加载来源与真实工具动作 |
| 客户端版本兼容记录 | 明确哪些入口在具体版本和设置下完成了验收 | 记录规则来源、操作系统、客户端版本和实际新对话行为 |
| 安装选择与策略的可发现性 | 降低首次配置和升级时的理解成本 | 结合真实使用反馈完善选择说明与体检建议，保持旧配置可迁移 |

项目分支策略和人工接管流程已实现并完成上述工具层验证。跨机器协作、同文件行级并行与真实客户端验收仍不在这些结果的覆盖范围内。
